# Deployment

One Docker image serves the API and the built SPA. It is deployed to two targets, Render and AWS, by `.github/workflows/deploy.yml` after CI and E2E are green on `main`. CD details (jobs, secrets and variables): [`deploy/README.md`](../deploy/README.md). Per-target details: [`deploy/render/README.md`](../deploy/render/README.md), [`deploy/aws/README.md`](../deploy/aws/README.md). Operations (live check, rollback, key rotation): [`_docs/deploy-runbook.md`](../_docs/deploy-runbook.md). App configuration reference: [`docs/developer-guide.md`](developer-guide.md). Merge flow, smoke checks and rollback: [release-process.md](release-process.md). What CI and E2E check before a deploy: [testing.md](testing.md).

## Docker image

`Dockerfile` (3 stages): Node 22 builds `frontend/dist`; Go 1.26 builds `mg-server` (`CGO_ENABLED=0`); an `alpine:3.20` runtime holds the binary and the SPA in `/app/public`, runs as non-root user `app`, and defaults to `PORT=8080 STATIC_DIR=/app/public DB_DRIVER=postgres STORE=db`. `HEALTHCHECK` calls `GET /health`.

```
docker build -t mg:local .
```

## Docker Compose with Postgres

`docker-compose.yml` runs `app` (built from the Dockerfile, published on `${APP_PORT:-8080}`) and `db` (`postgres:16-alpine`, named volume `pgdata`). `app` waits for the `db` healthcheck.

Create a git-ignored `.env` with the required names below (compose refuses to start if a required one is missing), then:

```
docker compose up -d --wait
docker compose down        # keep data
docker compose down -v     # also delete the pgdata volume
```

For plain HTTP on localhost set `COOKIE_SECURE=false` (empty also works but logs a warning).

## Environment variables (names only)

| Name | Where | Notes |
| --- | --- | --- |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | compose, required | Used by `db` and to build the app's `DATABASE_URL` |
| `JWT_SECRET` | all targets, required | 32+ bytes; the backend refuses to start with less. Compose: `.env`. Render: generated by the Blueprint. AWS: SSM `/<stack>/jwt-secret`, written into the instance's `app.env` by `remote-deploy.sh` |
| `DATABASE_URL` | app, when `STORE=db` and `DB_DRIVER=postgres` | Built by compose; `fromDatabase` on Render; written by the instance user data on AWS |
| `STORE`, `DB_DRIVER` | app | `db`/`memory`; `postgres`/`sqlite` |
| `APPLY_SCHEMA` | app, optional | `true` applies the embedded `backend/db/schema.sql` at startup (set on Render) |
| `COOKIE_SECURE` | app | `true` behind HTTPS (Render sets it; on AWS only with `DomainName`); unset logs a warning |
| `APP_ENV` | app, optional | environment label `[a-z0-9-]{1,16}`, default `local`; `dev` on Render (`render.yaml`), `prod` on AWS (`remote-deploy.sh`) |
| `TRUSTED_PROXY_HOPS` | app, optional | number of reverse proxies in front of the app, 0-5, default 0 (invalid: 0 with a warning); the login/register limiter then takes the client from `X-Forwarded-For`, counted from the right. `1` on AWS (`remote-deploy.sh`, Caddy only), not set on Render until measured, compose passes it (default 0); see `_docs/rate-limiter.md` |
| `APP_COMMIT` | app, optional | `X-Build` value when `RENDER_GIT_COMMIT` is absent; set to the sha by the AWS rollout |
| `PORT`, `STATIC_DIR` | app | Image defaults 8080 and `/app/public` |
| `METRICS_ADDR` | app, optional | Separate listener for `/metrics`; see `_docs/plan.md` |
| `APP_PORT` | compose | Host port, default 8080 |
| `REGISTER_MAX_PER_IP` | compose, test stacks only | Raises the per-IP register limit |
| `SQLITE_PATH`, `DB_MAX_CONNS`, `DB_STATEMENT_TIMEOUT` | app, optional | See `docs/developer-guide.md` |

## Schema and migrations

The Postgres store does not create tables. There is no migration tool, only `backend/db/schema.sql`, which is idempotent (`CREATE ... IF NOT EXISTS`). Schema changes that are not additive need a manual migration.

- **Compose:** the file is mounted at `/docker-entrypoint-initdb.d/001-schema.sql`. Postgres runs it only on the first start of an empty `pgdata` volume. Later edits to `schema.sql` are not applied to an existing volume; either apply the file by hand (`psql ... -f backend/db/schema.sql`) or recreate the volume with `docker compose down -v` (destroys data).
- **Render:** the Blueprint sets `APPLY_SCHEMA=true`, so the server applies the embedded `schema.sql` at every startup (advisory lock, short lock timeout; see `_docs/deploy-render.md`).
- **AWS:** every rollout applies `backend/db/schema.sql` with `psql` inside the `mg-db` container before the app container is recreated (`deploy/aws/remote-deploy.sh`).

## Environments

| Environment | Target | Changes through | `APP_ENV` |
| --- | --- | --- | --- |
| dev | Render | `deploy.yml`, automatically on every green `main` commit | `dev` |
| prod | AWS `micro-git-prod` | `promote.yml` ("Promote to production"), manually, with approval | `prod` |

Each has its own database. `APP_ENV` (`[a-z0-9-]{1,16}`, default `local`, invalid falls back to `local` with a warning) is the `env` field of every JSON log line, the `env` label of `build_info` and the span resource attribute `deployment.environment`.

## Deploy workflow (`deploy.yml`, dev)

Trigger: `workflow_run` of `CI` or `E2E` completing on `main`. Job `gate` runs only if that run concluded `success`, was a `push`, and on `main`. It then queries `gh run list` for the same commit SHA and sets `ready=true` only if both `ci.yml` and `e2e.yml` have a completed `success` run. Whichever of the two finishes last sees both green, so one deploy starts per commit. `concurrency: deploy-main` does not cancel running deploys.

The gate also writes a true/false flag (never a value) for whether the Render hook is configured; `deploy-render` runs when `ready` and that flag are both true:

| Job | Enabled by | Type |
| --- | --- | --- |
| `deploy-render` (POST to the deploy hook, pinned with `ref=<sha>`), then `smoke` (waits for `X-Build` == sha on `/health`, then `/` 200) | `RENDER_DEPLOY_HOOK` | secret |

With the hook unset the workflow is a no-op. It does not deploy AWS.

## Promotion workflow (`promote.yml`, prod)

Manual (`workflow_dispatch`, run from `main`), input `sha` (empty = the commit dev serves now). Jobs: `resolve` (commit exists, is on `main`, CI and E2E green, equals dev's build unless typed), `approve` (environment `production`, required reviewer), `deploy` (environment `aws-prod`, `deploy/aws/deploy.sh --apply --ci --ref <sha>`), `verify` (X-Build on dev, and on prod when the variable `PROD_URL` is set). `concurrency: promote-production`. Details, secrets and failure behaviour: [`deploy/README.md`](../deploy/README.md#promote-to-production).

## Health check

`GET /health` returns 200 `OK` (also reachable as `/api/health`). Used by the Docker `HEALTHCHECK`, Render (`healthCheckPath`), the `smoke` job and the AWS checks in `deploy.sh`. Every response carries `X-Build` (`RENDER_GIT_COMMIT`, else `APP_COMMIT`, else `dev`). The compose `db` service uses `pg_isready`.
