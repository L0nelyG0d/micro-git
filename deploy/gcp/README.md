# GCP deploy (Terraform)

Used by `.github/workflows/deploy.yml`, job `deploy-gcp`. The job runs only when the repository variable `GCP_WORKLOAD_IDENTITY` is set and CI and E2E are green for the commit on `main`.

Terraform root: `deploy/gcp/` (written separately; the workflow runs `terraform init` and `terraform apply` there).

## Required GitHub setup

| Kind | Name | Purpose |
| --- | --- | --- |
| Variable | `GCP_WORKLOAD_IDENTITY` | Full resource name of the Workload Identity Provider (gate for the job) |
| Variable | `GCP_SERVICE_ACCOUNT` | Service account email to impersonate (deploy identity) |

## Workload Identity Federation

- Create a workload identity pool and an OIDC provider for `https://token.actions.githubusercontent.com`.
- Restrict the provider with an attribute condition to this repository (`assertion.repository == '<owner>/<repo>'`) and, if possible, to `main`.
- Grant `roles/iam.workloadIdentityUser` on the service account to the pool principal set for this repository.

No service account keys are stored in GitHub.

## Terraform state

The root must configure a remote backend (for example a GCS bucket) before the first `apply`; the workflow does not create it. Keep the bucket name in the Terraform backend block, not in secrets.

## Manual run

    cd deploy/gcp && terraform init && terraform apply

## What this creates

| Resource | File | Free tier |
| --- | --- | --- |
| APIs: compute, artifactregistry, iam, run | `main.tf` | Enabling APIs is free |
| Artifact Registry repo `mg` (Docker) | `main.tf` | 0.5 GB storage per month free; delete old tags |
| VM `mg-app`, `e2-micro`, Debian 12, 30 GB standard disk, ephemeral external IP | `main.tf` | e2-micro: 1 instance per month free in us-west1, us-central1, us-east1; 30 GB standard PD free |
| Firewall: 80/443 from anywhere; 22 only from the IAP range | `main.tf` | Free |
| VM service account (registry reader only) | `main.tf` | Free |
| Docker compose on the VM: Postgres 16, the app image, Caddy (TLS) | startup script in `main.tf` | Runs on the e2-micro |
| Cloud Run service `mg` (optional, `enable_cloud_run = true`) | `main.tf` | Free within Tier 1 limits; min instances 0 |

No Cloud SQL (not free), no load balancer, no static IP, no Cloud NAT, no VPC connector (all billable).

Cloud Run cannot run Postgres, and it cannot reach the VM's database without a paid VPC connector, so the optional Cloud Run service runs with `STORE=memory` (demo only). The VM is the real deployment.

## First-time steps

1. Create the state bucket by hand, then put its name in the `backend "gcs"` block in `main.tf` (replace `CHANGE-ME-mg-tfstate`).
2. `terraform init` and `terraform apply -var project_id=<project>`.
3. Push the app image (the root `Dockerfile`) to `<region>-docker.pkg.dev/<project>/mg/app:<tag>`:

       gcloud auth configure-docker <region>-docker.pkg.dev
       docker build -t <region>-docker.pkg.dev/<project>/mg/app:latest .
       docker push <region>-docker.pkg.dev/<project>/mg/app:latest

4. On the VM the app container pulls the image on boot. If the image was pushed later: `gcloud compute ssh mg-app --zone <region>-b --tunnel-through-iap`, then `cd /opt/mg && sudo docker compose pull && sudo docker compose up -d`.
5. Create the tables once (the app does not migrate Postgres itself). The `schema_command` output prints the exact command; it pipes `backend/db/schema.sql` into `psql` inside the `db` container.
6. Open `site_url` (output).

## Gotchas and tradeoffs

- **Secrets**: the DB password and `JWT_SECRET` are generated by Terraform (`random_password`). They live in the Terraform state (so the state bucket must be private) and in the VM startup-script metadata (readable by anyone with `compute.instances.get` on the project). Move them to Secret Manager if that is not acceptable; Secret Manager is free for a few active secrets but needs its own IAM.
- **IP changes**: there is no static IP. A stop/start or recreate changes the external IP, which breaks DNS for `domain`. Reserving a static IP is billable.
- **External IPv4 may be billed**: Google bills in-use external IPv4 addresses. Check the billing report after the first day.
- **Plain HTTP login**: with no `domain`, `COOKIE_SECURE` is false. Set `domain` before using the app from another machine over HTTPS.
- **Startup script re-runs on every boot** and only (re)starts the compose stack. Data persists in the `pgdata` Docker volume on the boot disk; `terraform destroy` deletes it.
- **Ports 80/443 open to the world**: Caddy terminates TLS. Port 5432 is never published.
- **The image serves the SPA and the API** (root `Dockerfile`, `STATIC_DIR=/app/public`, `/api` prefix stripped by `backend/static.go`). Caddy only forwards everything to `app:8080`.
- **Swap**: the e2-micro has 1 GB RAM; the startup script adds a 1 GB swap file.
- **CI (`.github/workflows/deploy.yml`, job `deploy-gcp`)** runs `terraform apply -auto-approve` on every green push to `main` and does not pass `project_id`. It fails until `TF_VAR_project_id` is set in that job (or a default is added). The `backend "gcs"` bucket must exist first.
- **Terraform not verified here**: `terraform` was not on PATH when these files were written, so `fmt` and `validate` have not been run. Run `terraform fmt -check -recursive` and `terraform validate` before the first apply.
