# Deploy on Render

Live URL: https://micro-git.onrender.com (health: `GET /health`).

## Blueprint steps
1. Render dashboard > New > Blueprint, connect the GitHub repo.
2. Set the Blueprint file path to `deploy/render.yaml`. It creates the Docker web service `micro-git` (root `Dockerfile`) and the Postgres database `mg-db`.
3. Apply. Render builds the image, injects the env vars below, and waits for `/health`.
4. For automatic deploys from CI: Service > Settings > Deploy Hook, copy the URL, and store it as the repository secret `RENDER_DEPLOY_HOOK` (the Deploy workflow runs it after CI and E2E pass on main).
5. Never create a new Blueprint against the live service: Render creates an independent, suffixed set of resources, and only one free Postgres is allowed per account. To manage the existing live service from the file, add the existing service to an existing Blueprint and check the sync preview before confirming (DATABASE_URL must stay linked to the live database and the generated `JWT_SECRET` must not be regenerated). The Blueprint service name is `micro-git`, matching the live service.

## Environment variables (names only)
- `STORE` (db), `DB_DRIVER` (postgres), `COOKIE_SECURE` (true): fixed in the Blueprint.
- `DATABASE_URL`: from the `mg-db` database (`fromDatabase`).
- `JWT_SECRET`: generated by Render (32+ bytes required).
- `APPLY_SCHEMA` (true): see Schema.
- Optional: `APP_COMMIT` (X-Build fallback when `RENDER_GIT_COMMIT` is absent), `PORT`, `DB_MAX_CONNS`, `DB_STATEMENT_TIMEOUT`.

## Schema
A fresh Render Postgres has no tables. With `APPLY_SCHEMA=true` the server runs the embedded `backend/db/schema.sql` at startup through the pgx pool. The script is idempotent (`IF NOT EXISTS`), so it is safe on every boot. The GORM store (AutoMigrate) is SQLite only, so it is not used for Postgres. Schema changes that are not additive need a manual migration.

## APP_URL and the smoke job
The `smoke` job in `.github/workflows/deploy.yml` runs after a successful deploy job. It runs only after `deploy-render` succeeded. It polls `$APP_URL/health` for about 8 minutes until the `X-Build` response header (the server sets it from `RENDER_GIT_COMMIT`, else `APP_COMMIT`, else `dev`) equals the deployed commit, so an old instance cannot pass; then it checks `/` returns 200. It never registers users. `APP_URL` is a repository variable (Settings > Secrets and variables > Actions > Variables); if unset it defaults to `https://micro-git.onrender.com`. A failing smoke job fails the workflow when it runs.

## Rollback
Render dashboard > the service > Events/Deploys > pick the previous successful deploy > Rollback (or Redeploy). The schema is additive, so older builds keep working against it.

## Secret rotation
- `JWT_SECRET`: Service > Environment > edit (or regenerate) > save. Redeploys; existing sessions are signed out.
- Database password: Render dashboard > `mg-db` > rotate/reset credentials; `DATABASE_URL` is re-linked by the Blueprint, then redeploy the service.
- `RENDER_DEPLOY_HOOK`: regenerate the hook in Service settings and update the GitHub secret.

Note: git history still contains credential-bearing files that were removed from the tree (session exports, `resolving the issues.txt`). The database credential has not been rotated; treat rotation as a follow-up.
